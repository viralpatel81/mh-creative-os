brand — the 112 files, decoded

Brand has one job: take a brand definition and a topic, produce a brief.v1. Everything else in those 112 files exists to make that one job autonomous, safe, and self-improving. Here are all 15 capability areas grouped by their role in the workflow.

Quick map

  1. Foundation — the things that don't run, they just exist (5 areas)
  2. Input pipeline — what feeds the planner (2 areas)
  3. The core workflow — plan → produce → eval → publish (4 areas)
  4. Operations — what keeps it running 24/7 (4 areas)
  5. How it all fits together — the autonomous loop
layer 1 · foundation

Foundation — the things that don't run, they just exist

These are the parts every other capability reads from. They define who the brand is, who is writing for it, what the rules are, and how to talk to the outside world. Nothing here generates content — it's all definitions and connectors.

core/ — the brand's "self"
11 files

Where the brand's identity, configuration, policies, and shared state live.

brands.py loads brands/<id>/brand.md into a typed object. config.py holds suite-wide settings. identity.py tracks brand identity (name, voice, positioning). policy.py is the guardrail engine — every autonomous action runs through it and gets back ALLOW / ESCALATE / DENY. decision.py is the audit log — every choice the system makes gets recorded with a type, status, and timestamp. learning.py tracks outcomes so the brand learns what worked. storage.py manages where files live on disk. llm.py wraps LLM calls. signals.py, evaluation.py are shared types.

files: brands · config · identity · policy · decision · learning · storage · llm · signals · evaluation
agents/ — specialist subagents
4 files

Two specialist AI agents the brand can call on. Both inherit from a common base.

base.py defines what an agent is (a class that takes input, calls an LLM with specific tools, returns structured output). market.py is the market-research agent — competitors, trends, segments. threat.py is the risk-scanning agent — flags PR risks, legal issues, off-brand statements before they ship.

You can add a third specialist (e.g. "compliance" or "legal") by subclassing the base — no rewrite needed.

files: base · market · threat
persona/ — brand-local persona system
11 files

A second persona system that lives inside brand. (Yes, this is duplication with the top-level persona module.)

Same shape as the top-level persona module — bootstrap, chat, crud, drift, enrichment, exporters, learning, optimization, storage. Originally the top-level persona module split off from this. The duplication is a known sharp edge — see the warning on the main brand page.

Practical impact: the rest of the suite reads voice_pack.v1 from the top-level module; this folder is brand's own local fallback when there's no exported voice pack to read.

files: bootstrap · chat · cli · crud · drift · enrichment · exporters · learning · optimization · storage
adapters/ — bridges to the outside world
4 files

Translators between brand's internal types and external systems.

brandos.py talks to brand-os (the sister system that owns brand templates). persona.py imports voice packs from the top-level persona module. social.py abstracts away the differences between social platforms (Twitter shapes posts differently than LinkedIn).

files: brandos · persona · social
server/ — optional HTTP surface
3 files

If you don't want to use the CLI, brand exposes itself over HTTP.

api.py is a REST server. mcp.py is a Model Context Protocol server — Claude or other AI clients can call brand's tools directly.

Most use cases never touch this. It exists so the same brand module can be embedded inside other applications.

files: api · mcp
layer 2 · input pipeline

Input pipeline — what feeds the planner

Before the brand can plan a brief, it needs to know what's happening in the world that matters to it. These two areas pull in raw inputs and decide what's actually worth acting on.

signals/ — what's the world saying?
13 files

Monitors the outside world for things this brand should know about. Like Google Alerts, but smarter.

sources/ contains the data feeds: rss, reddit, reddit_discover. providers/ wraps third-party APIs: google_news, web (general scraping), file (local docs as a source). relevance.py scores each incoming signal — is this actually relevant to this brand's pillars? history.py remembers what's been seen so the system doesn't react to the same news twice. schema.py defines what a "signal" looks like as a typed object.

in: RSS feeds, Reddit threads, Google News, web pages → out: scored, deduplicated signals
files: cli · history · relevance · schema · providers/{file,google_news,web} · sources/{reddit,reddit_discover,rss}
intel/ — deep dives on what signals surface
8 files

When a signal is interesting, intel goes deep. Scrape pages, extract entities, find outliers.

pipeline.py orchestrates the deep-dive flow. scrapers/ — web.py for generic scraping, apify.py for the Apify platform (handles auth walls, dynamic content). outliers.py finds anomalies in the scraped data (unusually viral threads, suspicious sentiment spikes). hooks.py lets you plug custom logic in at specific points.

in: a high-relevance signal → out: enriched context (full page contents, entities, anomalies)
files: cli · hooks · outliers · pipeline · scrapers/{apify,web}
layer 3 · core workflow

The core workflow — plan → produce → eval → publish

This is the heart of the brand module. The journey from "a topic" to "a published post" runs through these four stages in order. The first stage (plan) produces the brief.v1. The next three turn that brief into actual content and ship it.

plan/ — turns a topic into a brief.v1
13 files

The most important module in brand. This is where the brief.v1 artifact gets built.

brief_v1.py defines the Pydantic types for brief.v1 (the spine artifact). stages/ runs the 4-step planning pipeline: research (competitors, sources, segments) → strategy (audience, pillars, angle, CTA) → creative (headlines, copy, assets) → activation (channels, calendar, KPIs). stages/normalize.py collapses these verbose stage outputs into the lean brief.v1 shape. plugins/ — seo.py and social.py add domain-specific guidance. store.py persists every plan run so you can replay any prior brief.

in: brand.md + voice_pack.v1 + topic + signals → out: brief.v1.json
files: brief_v1 · cli · store · stages/{research,strategy,creative,activation,normalize} · plugins/{seo,social}
produce/ — turns a brief into actual content
14 files

Given the brief, draft the post: text copy, generated image, generated video.

copy.py drafts post text in the voice from the voice pack. image/ generates images — generate.py is the orchestrator, providers/ wraps OpenAI / Gemini / Stability. video/ does the same for video. queue.py queues content for later publishing — useful for scheduled drops or rate-limited platforms.

Note: there's overlap with the TypeScript studio module's render pipeline. The Python produce/ path is for content that stays inside brand (drafts, queues, pre-publish previews); the TS studio/ path is for final renders that get published. They share concepts but aren't the same code.

in: brief.v1 → out: draft post + media files
files: cli · copy · queue · image/{generate,providers} · video/{generate,providers}
eval/ — is this draft good enough?
6 files

Score the drafted content against a rubric. If it fails, fix it.

rubric.py defines the scoring criteria (voice fidelity, on-brand, claim safety, hook strength). grader.py is the LLM-based grader that scores a draft against the rubric. heal.py takes a failed draft + the rubric findings and tries to fix it automatically. learnings.py persists what the eval found, so the system gets sharper over time.

in: draft post + brand rubric → out: pass/fail score, healed draft if needed
files: cli · grader · heal · learnings · rubric
publish/ — push it out to the world
11 files

Send the approved post to social platforms. This is brand's own publish path (separate from studio's TS publish path).

platforms/ has direct adapters for each: twitter, linkedin, facebook, instagram, threads, youtube. queue.py manages scheduled and immediate posts. rate_limit.py enforces per-platform rate limits so you don't get banned.

Why both brand and studio have a publish path: brand's is for Python-only setups (no Node), studio's is the canonical path with full SQLite-backed run engine. Most users will end up using studio.

in: approved draft → out: post ID from the platform + decision log entry
files: cli · queue · rate_limit · platforms/{facebook,instagram,linkedin,threads,twitter,youtube}
layer 4 · operations

Operations — what keeps it running 24/7

The core workflow runs once per topic. These four areas turn it into a daemon — continuous signal monitoring, autonomous decisions inside policy guardrails, human escalation when needed, and post-publish monitoring.

loop.py + loop_cli.py — the autonomous daemon
root files

The thing that runs continuously in a container. Wakes up, checks signals, makes decisions, posts content, sleeps, repeats.

Design pattern they use: "human-over-the-loop" (not human-in-the-loop). Humans set the policies and thresholds; the system operates autonomously within them. When something falls outside policy, it escalates to a human queue. Otherwise it just runs.

The loop ties together: signals (what's happening) → policy.py (am I allowed to act?) → plan (what should I make?) → produce → eval → publish → decision.py (log what I did) → learning.py (track outcomes).

root files: loop · loop_cli · cli · cli_utils
monitor/ — watching what happened after publish
4 files

Once content is live, track how it performs and whether the brand is being talked about correctly.

reports.py generates periodic brand health reports. emailer.py sends them out. Combined with monitor's drift detection, this is brand's read-channel — it knows what's happening to the brand in the world, not just what it's publishing.

in: published posts + ongoing signals → out: health reports, drift alerts
files: cli · emailer · reports
actions/ — atomic things the loop can do
3 files

Two specific actions the loop can take that aren't full workflows: write something, or notify someone.

write.py = produce content of any kind. notify.py = send a notification (email, Slack, etc.). These exist so the policy engine can describe permitted behaviors at a fine grain ("this brand can write autonomously but must escalate notify").

files: notify · write
workflows/ — human-in-the-loop approval flows
2 files

When the policy engine returns ESCALATE, the work doesn't get dropped — it goes into an approval workflow.

approval.py manages the queue of pending decisions awaiting human review. A human sees the proposed action, the context, the policy reasoning, and approves or rejects.

Approved items flow back into the loop and execute. Rejected items get logged as decision.status = denied and the system learns from the pattern.

files: approval

How it all fits together — the autonomous loop

This is the picture of brand running unsupervised, every minute of the day. Everything you read above plugs in here.

What this actually looks like in time

[09:00:00] loop wakes up [09:00:01] signals/ — pulls last hour: 142 new items (RSS, Reddit, Google News) [09:00:02] signals/relevance — scores them, keeps 7 above threshold [09:00:03] intel/ — deep-dives the top 2 (full page contents, entity extraction) [09:00:05] core/policy — "should I plan content for these?" → ALLOW [09:00:06] plan/ — runs research → strategy → creative → activation → normalize [09:00:42] ✓ brief.v1 written to disk (this is the spine artifact) [09:00:43] produce/ — drafts copy in Ashton's voice, generates image [09:01:18] eval/ — scores draft against rubric: voice 0.91, on-brand 0.88, claim-safe 0.95, hook 0.72 → PASS [09:01:19] core/policy — "publish to twitter+linkedin+ig?" → ALLOW (autonomous) [09:01:20] publish/ — posts to 3 platforms via direct adapters [09:01:24] ✓ all 3 succeeded — IDs logged [09:01:25] core/decision — appended to audit log (type=content_publish, status=success) [09:01:26] core/learning — outcome stub recorded, awaits real engagement data [09:01:27] loop sleeps 60 minutes [09:33:00] — meanwhile, a new signal scores 0.97 and triggers an off-cycle wake — [09:33:01] plan/ runs again on the new topic [09:33:55] eval/ — hook score 0.41 — FAIL → heal.py rewrites [09:34:20] eval/ — second draft passes [09:34:21] core/policy — "publish?" → ESCALATE (sensitive topic detected by threat agent) [09:34:22] workflows/approval — queued for human review [09:34:23] actions/notify — emails the brand owner [10:42:00] — human approves the queued item from web UI — [10:42:01] publish/ — pushes to platforms [10:42:08] core/decision — logged as approved-after-escalation
The thing to notice: every box in the diagram is touched in a normal hour of the loop. Foundation reads happen everywhere. Input pipeline runs continuously. Core workflow runs each time a topic fires. Operations wrap and govern the whole thing. 112 files is not bloat — it's the surface area of running a brand autonomously, with safety, with audit, with learning.

How to read this for quality judgment

Sign that this is well-engineered: the layers are clean. Foundation has no dependencies on input or workflow. Workflow has no dependencies on operations. Operations call into workflow, not the other way around. You can excise the operations layer and the rest still works as a one-shot CLI tool. That's separation of concerns done right.

Sign of accumulated complexity: the brand/persona/ folder duplicates the top-level persona module. The brand/publish/ path duplicates studio's publish path. These are the seams where the system has been refactored and the old code hasn't been deleted yet. In an audit, you'd flag these — they're not bugs, but they're tech debt that will eventually need cleanup.

Sign of real autonomy thinking: the policy engine returns three verdicts (allow / escalate / deny), not just yes/no. The decision log is a typed enum with eight specific decision types. The learning module ties outcomes back to decisions. This is what a system that has actually been run in production looks like — most "autonomous AI" repos have none of this scaffolding because they've never run unsupervised for long enough to need it.
