metrics

The feedback loop. Reads what actually happened after publishing, normalizes it, and feeds it back to forecast as calibration data. Small module — only 6 files — but it's what turns this from a generator into a learning system.

What it actually does

Two operations, two commands:

CommandWhat it does
metrics adaptTake a run_result.v1 (what the studio published) + a sidecar JSON of realized engagement (likes, shares, comments, click-through) and produce a performance.v1 artifact in a normalized shape. This is just data plumbing — read messy real-world numbers, output clean schema-conformant ones.
metrics calibrateTake a forecast.v1 (what we predicted) + the performance.v1 (what actually happened) and emit calibration data. This tells the forecast module which scenarios were close and which were wrong, so the next forecast for this brand can update its priors.
This is the loop-closing module. Without metrics, the suite is a generator — it predicts, it publishes, and forgets. With metrics, every published post becomes training data for the next forecast. The system gets better at predicting this specific brand's audience over time.

The loop, made literal

The Shepherd Boy Farms example

The sidecar (what you'd give it from real-world data)

{ "run_id": "sbf.run.2026-05-12.001", "window": "7d-post-publish", "by_platform": { "twitter": { "likes": 287, "reposts": 14, "replies": 22, "impressions": 9100 }, "linkedin": { "likes": 96, "reposts": 4, "replies": 8, "impressions": 2300 } } }

The adapt command

$ uv run agentcy metrics adapt \ --run-result brands/shepherdboyfarms/output/runs/sbf.run.2026-05-12.001.json \ --sidecar engagement.json \ --json

What comes out — performance.v1.json

Strict, narrow schema. The CLAUDE.md note on this one is unusual:

"This first slice is intentionally limited to aggregate performance snapshots for published social.post outcomes only and excludes tokens, secrets, auth material, audience-level data, and user-level PII."

That's a deliberate scope cut — it would have been easy to also include per-user analytics, but the schema author explicitly bounded it to aggregate-only. That's a thoughtful privacy/scope decision baked into the contract.

The calibrate command

$ uv run agentcy metrics calibrate \ --forecast brands/shepherdboyfarms/output/forecasts/sbf.fc.2026-05-12.001.json \ --performance brands/shepherdboyfarms/output/perf/sbf.perf.2026-05-19.001.json \ --json

Output: a calibration record showing which forecasted scenario was closest to reality, by how much, and what to update. Next time you run a forecast for this brand, those priors get pulled in.

Why this small module is the most important one

It's the gradient signal. Without metrics, the forecast module is making predictions into a void — there's no way to know if it's getting better or worse. With metrics, every cycle produces a measured outcome that updates priors. The whole suite becomes self-improving rather than self-reinforcing.

It's also the cheapest module to audit. 6 files. ~3 test files. You can read the entire module in 20 minutes. If the design here is sloppy, the whole loop is unreliable. If it's clean, the suite has a real feedback channel. (Spoiler: it's clean. Strict schemas, explicit privacy scope, no PII.)

The CLAUDE.md scope note is a quality signal. The comment about excluding tokens/auth/PII isn't there by accident — someone thought hard about what should NOT be in this artifact. That's the kind of restraint that's rare in AI repos, which usually pile features into every module until the schemas drift.

The bottom line: if a creative-AI repo you're evaluating has nothing equivalent to this — no module that compares predicted vs. realized — then it's a generator, not a learning system. They might look similar in a demo, but they diverge sharply over time. This is the single most important module to look for when judging depth.
