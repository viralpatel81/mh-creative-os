studio

The only TypeScript module. Takes the brief, renders the actual image or video, drafts copy, and publishes directly to social platforms. SQLite-backed run engine. Remotion for video.

What it actually does

Studio is where the suite stops thinking and starts producing files and HTTP requests. Three responsibilities:

  1. Generate — LLM writes copy + selects assets based on the brief's creative direction.
  2. Render — produces actual PNG/MP4 files from the brand's design tokens. Images via Gemini + custom social/card compositors. Video via Remotion (React-for-video).
  3. Publish — pushes the rendered post to Twitter, LinkedIn, Facebook, Threads, or Meta's Graph API, using direct adapters (no Buffer/Hootsuite middleware).

The whole thing runs on a SQLite-backed engine. Every run is a row; every step within a run is a row. You can replay, resume, or roll back.

Why TypeScript here: rendering is a Node/browser problem (canvas, Remotion, sharp), and the publish APIs all have first-class JS SDKs. Splitting at this seam keeps the "think" side (Python LLMs, graphs, simulations) clean and the "ship" side (file system, image bytes, HTTP) idiomatic.

The folder structure — 47 TypeScript files

brands/ (2 files)

  • Parses brand.md + design.md from brands/<id>/
  • Validates frontmatter against the runtime schema
  • This is the bridge between human-edited markdown and machine-consumed objects

generate/ (3 files)

  • LLM pipeline that drafts post copy from the brief
  • Picks format (standard, comparison, BTS, quote-card)
  • Generates the image prompt from design.md's template

render/ (7 files)

  • social.ts — composes a social image with text overlay
  • card.ts — quote-card or hero-stat treatments
  • gemini.ts — Gemini image gen integration
  • dither.ts, colors.ts, fonts.ts — helpers
  • video/ — Remotion compositions for motion content

publish/ (7 files)

  • twitter-direct.ts — direct Twitter API v2
  • linkedin-direct.ts — direct LinkedIn UGC API
  • facebook-direct.ts — direct Pages API
  • meta-graph.ts — Meta Graph API (Threads, Instagram)
  • social.ts — adapter dispatch by platform
  • rate-limit.ts — per-platform rate limiter
  • base.ts — abstract adapter contract

runtime/ (4 files)

  • SQLite engine — runs, steps, artifacts, status
  • Workflow registry — social.post, video.post, etc.
  • Step persistence — every state transition recorded
  • Resume + replay semantics

commands/ (9 files), cli/ (2)

  • CLI surface: run, draft, render, publish, queue, replay, status, brands
  • Maps to agentcy studio <cmd> through the wrapper

core/ (6 files)

  • Shared types, config loading, error handling
  • The protocol artifact reader (run_result.v1 writer)

lab/ (2 files), domain/ (3)

  • Experimentation harness for testing new render styles
  • Domain types (Post, Asset, Schedule)

The Shepherd Boy Farms example

Command

$ uv run agentcy studio run social.post \ --brand shepherdboyfarms \ --brief-file brands/shepherdboyfarms/output/briefs/sbf.brief.2026-05-12.001.json \ --json

What happens internally

step 01 load brand → brands/shepherdboyfarms/{brand,design}.md → ✓ step 02 load voice_pack → input/voice_pack.v1.json → ✓ step 03 generate copy (LLM, using Ashton's voice) → ✓ step 04 generate image prompt from design.md template → ✓ step 05 render image via Gemini → output/renders/post-001.png → ✓ step 06 publish.twitter-direct → posted (id: 1234...) step 07 publish.linkedin-direct → posted (id: 5678...) step 08 write run_result.v1 → output/runs/sbf.run.2026-05-12.001.json → ✓

The output — run_result.v1.json

The largest schema (215 lines). Required: artifact_type, run_id, brief_id, brand_id, writer, workflow, status, started_at, completed_at. Optional: review, delivery, current_step, parent_run_id.

The interesting design choices

Direct adapters, not aggregators. Most "post to social" tools route through Buffer, Hootsuite, or Zapier. Studio talks directly to each platform's API. That's more work (5 adapters to maintain) but gives you control over scheduling, rate limits, and error handling, and avoids paying for a middleman.

Remotion for video. Video isn't an afterthought — it's a first-class workflow with React-based compositions in render/video/. The same brand design tokens drive both image and video, so a post looks consistent across formats.

SQLite is the right call. Every run + every step is a row. No need for Postgres for a CLI app, but you get full replay, resume, and audit for free. Most workflow systems either log to stdout (lost) or require a cloud DB (overkill).

The workflow registry. social.post is just one workflow. You could add video.post, email.send, blog.publish, each as a TypeScript file that defines its steps. The runtime engine doesn't care what the workflow is — it just executes steps and records state.
